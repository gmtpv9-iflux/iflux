```text

  ├── Enrich: sector_id, ecosystem_id, lot_threshold
  ├── Classify subject (§4.3.3) → field `subject` trong payload
  ├── Ghi Redis stock:{ticker} (single writer — §19.2)
  └── Publish Kafka topic: [ticks]  ← normalized + enriched
        ↓
   ┌────┴────────────────────────┬────────────────────────┐
   ▼                             ▼                        ▼
Money Flow Engine      Synthetic Index Engine       Alert Engine
(dùng subject sẵn)     (Tính Ig/Pg/Breadth)         (Match conditions)
   │                             │                        │
   └────────────┬────────────────┴────────────────────────┘
                ▼
Kafka topics: [flow-updates], [index-updates]
                │                        │
                │                        └──▶ [alert-triggers] → Notification Service (FCM/APNs)
                │
        ┌───────┴───────────────┐
        ▼                       ▼
WebSocket Gateway         Persistence Worker
(ticks, index, flow)      (Redis → TimescaleDB cuối phiên)
        │
        ▼
App clients (WSS)         API Layer / Web (poll)
```

## 2. TICK PROCESSING PIPELINE (CORE FLOW)

### 2.1 Ingestion Flow (Data Ingestion Service)

1. Nhận lệnh khớp từ Data Provider.
2. **Normalize:** validate schema, gán `event_id` (UUID v4).
3. **Clock Skew:** reject hoặc flag tick lệch quá ngưỡng (§18.3).
4. **Enrich:** tra cứu `sector_id`, `ecosystem_id`, `lot_threshold` từ Redis/PostgreSQL cache.
5. **Classify Subject:** gán `subject` (`foreign`, `retail`, `institutional`, `proprietary`) theo metadata tài khoản — **owner duy nhất: Data Ingestion** (§4.3.3, Contract §3.2.1).
6. **Redis write:** `HSET stock:{ticker}` — writer duy nhất (§12).
7. **Publish:** bọc Standard Envelope → Kafka topic **`ticks`**.
   * **Partition key:** `{ticker}` — ordering per-stock (Contract §3.2).

> **Dedup KHÔNG tại Ingestion.** Dedup `event_id` thực hiện tại **Engine consumer** qua Redis `dedup:flow:*` / `dedup:index:*` (Contract §3.1, Tech Spec §6.1).

### 2.2 Engine Consumption

Các Engine **chỉ subscribe `ticks`** — không re-classify `subject`, không tạo topic trung gian.

## 3. LATE TICK FLOW

SoT: Tech Spec §17.2.

```text
Data Ingestion nhận tick:
    matched_at vs current_session_date

    date(matched_at) == today
        → publish `ticks` → xử lý RT bình thường

    date(matched_at) == yesterday (1 session late)
        → publish `ticks.late`
        → Late Tick Processor: ghi TimescaleDB trực tiếp (bypass Redis accumulation)
        → log cho reconciliation

    older than 1 session
        → publish `ticks.dlq` (reason=too_old)
        → manual review
```

## 4. REAL-TIME STATE UPDATE FLOW

### 4.1 Redis Update (Single Source of Truth Intraday)

* Mọi thay đổi trong phiên **BẮT BUỘC** ghi Redis trước khi Engine emit update event.
* **Luật:** Redis CHỈ lưu trạng thái phiên hiện tại — không xử lý logic lịch sử tại đây.
* **Rebuild:** Khi Redis mất state intraday → **Kafka replay** từ offset ~09:00 ICT (§14.1, §6.1) — **bounded:** chỉ đầy đủ nếu Kafka retention + feed còn nguyên (§17).

---

## 5. MONEY FLOW ENGINE FLOW

### 5.1 Thứ tự xử lý

1. Nhận message từ topic **`ticks`** (đã có `subject`).
2. **Dedup:** `SETNX dedup:flow:{event_id}` TTL 24h — skip nếu đã xử lý (§6.1).
3. **Delta:** `buy_value` / `sell_value` theo Active Buy/Sell logic (§4.3.3).
4. **Atomic Write:** `INCRBY` Redis key `flow:*`, cập nhật ranking ZSET.
5. **Emit:** publish `flow-updates` lên Kafka.

### 5.2 Quy tắc đảm bảo

* Idempotency qua `event_id` — replay Kafka không double-count.
* Large Lots: cùng consumer path, threshold từ `stock:{ticker}` (§6.2).

---

## 6. SYNTHETIC INDEX ENGINE FLOW

### 6.1 Nguồn kích hoạt

* **`ticks`:** giá/volume mã thành viên thay đổi.
* **`ecosystem-changed`:** Admin thêm/xóa mã → reload member list + divisor.

### 6.2 Xử lý tính toán

1. **Dedup:** `SETNX dedup:index:{event_id}` TTL 24h.
2. Load member list từ Redis cache (`sector:{id}:members`, `ecosystem:{id}:members`).
3. Đọc giá hiện tại từ `stock:{ticker}` (read-only).
4. Tính **Ig**, **Pg**, **Breadth**.
5. Ghi `index:sector:{id}` / `index:ecosystem:{id}` (single writer — §12).
6. Publish `index-updates`.

## 7. ALERT ENGINE & NOTIFICATION SERVICE FLOW

### 7.1 Alert Engine

**Input:** `ticks`, `index-updates`, `flow-updates` (§9.1).

1. Load active alerts từ PostgreSQL → in-memory inverted index (§9.2).
2. Match event → kiểm tra cooldown Redis `alert:cooldown:{id}` (§9.4).
3. Publish `alert-triggers` lên Kafka.

### 7.2 Notification Service

```text
Kafka [alert-triggers]
        ↓
Notification Service
    ├── Dedup notification (§9.x)
    ├── FCM (Android)
    ├── APNs (iOS)
    └── Email fallback (nếu cấu hình)
```

> **WebSocket Gateway KHÔNG consume `alert-triggers`.** Push notification đi qua Notification Service — không fanout qua WSS (Tech Spec §8.1.1, §9.1).

## 8. WEBSOCKET FANOUT FLOW

> **Message schema:** Contract Spec **§4.3** — envelope `{ channel, type, data }`.

1. WebSocket Gateway consume: **`ticks`**, **`index-updates`**, **`flow-updates`** (§8.1.1).
2. Channel Registry in-memory — route theo subscription client.
3. **Throttling:** batching window **200ms** — chỉ giữ bản mới nhất mỗi ticker/channel (§8.1.1).
4. **Constraint:** Gateway là lớp truyền dẫn thuần túy — **KHÔNG** query DB/Redis, **KHÔNG** tính toán nghiệp vụ.

**Consumer lag > 5s:** drop intermediate updates, giữ latest per channel (§16 monitoring).

## 9. PERSISTENCE & BATCH ROLLUP FLOW

> **Schema & flush contract:** Contract Spec **§1.3** (ownership, UPSERT key, batch size, idempotency). **Topic registry:** Contract Spec **§3.2**.

### 9.1 End-of-Session Flush (Persistence Worker)

| Job | Thời gian (ICT) | Nguồn | Đích DB | Ghi chú |
|---|---|---|---|---|
| `session-stock-ohlcv-flush` | 15:55–16:05 | Kafka `ticks` (session today) + validate `stock:{ticker}` | `stock_ohlcv` (1m) | UPSERT `(time, ticker, timeframe)` |
| `session-flow-flush` | 15:55–16:05 | Redis `flow:*:{session_date}:*` | `money_flow` | UPSERT `(time, entity_type, entity_id, subject)` |

* Batch: **500 rows/txn**; job marker `flush:done:{job}:{session_date}` — rerun idempotent (Contract §1.3).
* **Luật (NFR-A01):** không chạy query nặng trong giờ giao dịch (09:00–15:00).

## 10. DAILY RECONCILIATION

SoT: Tech Spec §17.1.

**Job:** `session-reconciliation` — **17:00** mỗi ngày giao dịch (sau `daily-ohlcv-rollup`).

```text
1. Lấy danh sách ticker đã giao dịch từ TimescaleDB (session_date = today)
2. So sánh với official trade list từ Data Provider (nếu có API)
3. Backfill ticker thiếu → TimescaleDB + log audit
4. Verify money_flow totals vs large_lots net
5. Alert nếu inconsistency > threshold
```

Mục đích: bắt gap sau Redis replay, Persistence Worker fail, hoặc late tick.

## 13. DEGRADED MODE

SoT: Tech Spec §16.1.

**Trigger:** Data Provider mất kết nối ≥ 10s **hoặc** Kafka down > 60s.

```text
1. Data Ingestion → system-events "feed-degraded" / "kafka-down"
2. API Gateway → Redis flag degraded_mode=true
3. API response: header X-Data-Status: degraded + field data_as_of
4. App: banner "Dữ liệu có thể chưa cập nhật"
5. WebSocket Gateway: dừng push RT (không push stale)
6. Chart lịch sử (1D+): vẫn hoạt động từ TimescaleDB

Recovery: feed-restored → xóa flag → engines tiếp tục từ tick mới
SLA: phát hiện ≤ 30s; banner ≤ 35s
```

## 14. FAILURE HANDLING MATRIX

SoT: Tech Spec §16.1–§16.5.

| Failure | Detection | User impact | Recovery | Data loss |
|---|---|---|---|---|
| **Data Provider mất** | ≤ 30s | Banner + frozen RT | Tự động khi feed restore | Không |
| **Kafka down < 60s** | Immediate | Minimal (local buffer) | Flush buffer ordered | Không |
| **Kafka down > 60s** | 60s | Degraded mode (§13) | PagerDuty + manual | Có thể tick trong period |
| **Redis restart** | Immediate | Spinner rebuild | **Kafka replay §6.1/§16.3 ≤ 2 phút** | Không nếu replay đủ window |
| **Engine crash** | 5s health | ~30s Ig/flow gap | K8s auto-restart + resume offset | Gap nhỏ |
| **DB Primary down** | Sentinel | API write errors | Replica promote ≤ 30s | In-flight writes |

### 14.1 Redis Crash — Chi tiết (Option A: Kafka Replay)

```text
1. Detect Redis empty / connection fail → alert
2. Money Flow + Synthetic Index → state-rebuild mode
3. Seek Kafka `ticks` → offset ~09:00 ICT today
4. Replay → current offset với dedup:event_id bật
5. Alert Engine: reload alert definitions từ PostgreSQL
6. WSS: push "rebuilding" cho client
7. Post-session: session-reconciliation audit gap (§10)
```

> **Giới hạn:** Rebuild hoàn chỉnh **chỉ** khi Kafka retention + feed nguồn còn đầy đủ. Kafka down > 60s → bounded gap — không claim 100% intraday.

### 14.2 Synthetic Index Engine Crash

1. Load divisor + members từ PostgreSQL.
2. Load giá từ Redis (nếu còn) hoặc Provider REST fallback.
3. Tính lại Ig → resume Kafka từ latest offset.
4. Downtime target: ≤ 30s.

## 15. EVENT ORDERING RULE (CRITICAL)

> **Ordering is guaranteed ONLY per ticker** (Kafka partition key = `{ticker}`).

* Toàn bộ lệnh HPG xử lý đúng thứ tự A → B.
* Dữ liệu cross-ticker (tổng flow sàn) = **eventual consistency** — lệch vài ms khi aggregate.

## 16. BACKPRESSURE & RETRY

SoT: Tech Spec §4.2.1 + §8.1.1 — **không** pause ecosystem theo CPU.

**Consumer retry (Money Flow + Synthetic Index):** Contract §3.11.

```text
Fail attempt 1 → ticks.retry.1s (retry_count=1)
Fail attempt 2 → ticks.retry.30s (retry_count=2)
Fail attempt 3 → ticks.dlq + Slack #engineering-alerts
```

**WebSocket throttling:** 200ms batching — overwrite intermediate tick, flush latest (§8).

**Consumer lag monitoring:** alert P1 khi lag > 5s; WSS drop intermediate, giữ latest.

## 17. SYSTEM GUARANTEES

* **No Double-count:** dedup `event_id` tại Engine + replay-safe (§5, §6).
* **Recoverable Intraday (bounded):** Redis state rebuild từ Kafka replay **khi** topic `ticks` còn đủ retention (24h) **và** Data Provider không mất tick trong window down. Nếu Kafka down > 60s hoặc buffer overflow → **gap có thể xảy ra** — `session-reconciliation` (§10) backfill sau phiên.
* **Single Writer:** mỗi Redis key một owner (§12); DB historical flush một owner (Contract §1.3).
* **At-least-once Kafka:** consumer idempotent (Contract §3.1).
* **Event Time Integrity:** OHLCV/flow/alert dùng `matched_at` (§11).

## 18. END-TO-END SUMMARY FLOW

**Provider** → **Ingestion** (normalize + enrich + classify) → **Kafka (`ticks`)** → **Engines (parallel, dedup)** → **Kafka (`flow-updates`, `index-updates`)** → **WSS / API** → **User**.

**Alert path:** Engines/events → **Alert Engine** → **`alert-triggers`** → **Notification Service** → FCM/APNs.

**Batch path:** Redis intraday → **Persistence Worker** → TimescaleDB → **rollup jobs** → historical API.

## 19. ROLE OF THIS FILE

Đây là **"Runtime Bible"** của iFlux. Lập trình viên:

* KHÔNG tạo topic `enriched-ticks` — dùng **`ticks`** enriched.
* KHÔNG classify `subject` tại Engine — owner = **Data Ingestion**.
* KHÔNG dedup tại Ingestion — dedup tại **Engine**.
* KHÔNG fanout `alert-triggers` qua WebSocket — qua **Notification Service**.
* KHÔNG bypass Redis cho RT — không đọc DB cho intraday state.
* KHÔNG ghi trực tiếp DB từ Engine tính toán.
* KHÔNG dùng TimescaleDB baseline cho Redis rebuild giữa phiên — **Kafka replay** (với bounded gap nếu mất tick).
* KHÔNG dùng Kafka topic ngoài **Contract §3.2 Registry**.

**Defer File 03 (Service Spec Sheets):** Admin mutation flows, subscription/entitlement, watchlist sync, analytics pipeline, deploy gate, service startup — chi tiết triển khai từng service.
