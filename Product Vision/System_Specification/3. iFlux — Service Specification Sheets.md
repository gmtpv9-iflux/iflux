## 0. ARCHITECTURAL INVARIANTS

### INV-S01 — Subject Classification Lifecycle

| Actor | Được phép | Cấm |
|---|---|---|
| **SVC-01 Data Ingestion** | **SET** field `subject` trên tick (duy nhất) | Đọc/sửa subject từ engine khác |
| **SVC-02, SVC-03, SVC-04** | **READ** `subject` từ `ticks.data` | Override, re-classify, default khác SoT |
| **SVC-11 Admin** | Sửa Sector/Ecosystem **membership**, divisor | Mutate subject taxonomy; API đổi enum subject GĐ1 |
| **Provider metadata change** | SVC-01 áp dụng rule §4.3.3 mỗi tick mới | Retroactive re-classify tick đã publish |

**Taxonomy GĐ1 (frozen enum):** `foreign` | `proprietary` | `institutional` | `retail` — Contract §3.4, Tech Spec §4.3.3.

**Khi Admin đổi Ecosystem/Sector:** chỉ ảnh hưởng enrich `sector_id` / `ecosystem_id` (lookup cache). Publish `ecosystem-changed` → SVC-02 reload. **Không** replay subject trên tick cũ.

**Enforcement:** Code review + unit test: Money Flow/Alert **reject tick** nếu `subject` null/invalid → `ticks.dlq`.

---

### INV-E01 — Event Identity & Idempotency Contract

| Layer | Key / Fingerprint | Store | TTL | Owner |
|---|---|---|---|---|
| Tick processing | `event_id` (UUID envelope) | `dedup:flow:{event_id}`, `dedup:index:{event_id}` | 24h | SVC-03, SVC-02 |
| Alert **evaluation** | `dedup:alert-eval:{alert_id}:{source_event_id}` | Redis SETNX | 24h | **SVC-04** |
| Alert **cooldown** | `alert:cooldown:{alert_id}` | Redis SETNX | 60s–300s | SVC-04 |
| Notification **delivery** | `dedup:alert-trigger:{alert_id}:{session_date}` | Redis SETNX | 24h | **SVC-06** |

**`alert-triggers` envelope bắt buộc trong `data`:**

```json
{
  "alert_id": 123,
  "user_id": "uuid",
  "source_event_id": "uuid-of-tick-or-index-or-flow",
  "trigger_fingerprint": "sha256(alert_id + source_event_id + matched_at)",
  "matched_at": "ISO8601"
}
```

**Luật replay Kafka:** Mọi consumer mutate state **phải** SETNX dedup trước khi ghi. Alert Engine **phải** dedup eval trước khi publish `alert-triggers` — không rely chỉ Notification.

### INV-SCH — Schema Version Enforcement Map

SoT schema: Contract §3.0–§3.13. Rule: Tech Spec §4.3.1.

| Service | Runtime hook |
|---|---|
| **SVC-01** | Produce `schema_version: "v1"`; reject publish nếu thiếu field bắt buộc |
| **SVC-02, SVC-03, SVC-04** | Consumer: `schema_version != supported` → `ticks.dlq` / skip + log |
| **SVC-06, SVC-09** | Consumer `user-events` / `alert-triggers`: reject unknown major version |
| **SVC-00 API Gateway** | REST: validate response builder không emit field ngoài Contract §4 |
| **SVC-08** | DB migration only via Admin deploy gate — không runtime mixed version |

**Breaking change process:** tăng `schema_version` → deploy consumer trước producer → Contract bump.

---

### INV-WSS — WebSocket Subscription State Contract

| Thuộc tính | Giá trị |
|---|---|
| **Owner state** | **SVC-05 WebSocket Gateway** — `ChannelRegistry` **in-memory per instance** |
| **Create** | Client gửi `subscribe` sau JWT handshake → Gateway validate tier (Contract §4.3, §4.5) → add `(channel → [conn_ids])` |
| **Destroy** | `unsubscribe`, connection close, hoặc `MAX_CHANNELS_EXCEEDED` (50) → remove entries |
| **Tier enforcement** | Gateway **từ chối** subscribe `flow:*:{subject}` chi tiết nếu JWT tier = free → error frame |
| **Reconnect** | Client **bắt buộc** Snapshot API (Contract §4.2) **trước** `subscribe` lại — Tech Spec §8.5 |
| **Cross-instance** | Không shared registry — mỗi pod owns local map; Kafka consumer group fanout |

**Cấm:** WSS query Redis/DB cho subscription list. Subscription authority = **client intent + JWT tier**, không phải User Service.

---

### INV-PER — Persistence Logical Separation

| Job group | Owner sheet | Domain | Schedule | Cấm |
|---|---|---|---|---|
| **Intraday flush (OLTP→TSDB)** | SVC-13 | `session-stock-ohlcv-flush`, `session-flow-flush` | 15:55–16:05 ICT | Gộp transaction với rollup |
| **Snapshot** | SVC-16 | `ranking-snapshot` | 16:30 | Mutate Redis |
| **Rollup (OLAP)** | SVC-16 | `daily/weekly/monthly-ohlcv-rollup` | §4.4 Tech Spec | Ghi Redis intraday |
| **Reconciliation** | SVC-16 | `session-reconciliation` | 17:00 | Sửa Redis RT state |

**Deploy GĐ1:** có thể **1 binary / 1 cron scheduler** — nhưng **4 job names riêng**, marker riêng (`flush:done:{job}:{date}`), **không** single mega-job.

## 1. LAYER A: MARKET RUNTIME CORE

### SVC-01: Data Ingestion Service

| | |
|---|---|
| **Tên Việt** | Dịch vụ Thu thập & Chuẩn hóa Dữ liệu |
| **Purpose** | Điểm nhập duy nhất thị trường + **executor duy nhất** phân loại Chủ thể |
| **Input** | Provider TCP/FIX |
| **Output** | Kafka `ticks`, Redis `stock:{ticker}` |
| **SLA** | p95 < 50ms tick→Kafka |

**Responsibilities**

1. Normalize, clock skew (§18.3), gán `event_id`.
2. Enrich `sector_id`, `ecosystem_id`, `lot_threshold` — reload lookup khi nhận signal cache invalidate (Admin / startup).
3. **Classify `subject`** — rule Tech Spec §4.3.3 — **INV-S01**.
4. Publish envelope `schema_version: "v1"` — **INV-SCH**.
5. Late tick routing → `ticks.late` / `ticks.dlq` (File 02 §3).

**Hard constraints:** Không service khác được ghi `subject` lên tick. Không API Admin đổi taxonomy GĐ1.

### SVC-04: Alert Engine

| | |
|---|---|
| **Input** | `ticks`, `index-updates`, `flow-updates` |
| **Output** | `alert-triggers` |
| **State** | In-memory inverted index (load PostgreSQL + LISTEN/NOTIFY) |

**Idempotency stack (bắt buộc thứ tự):**

1. Match condition → fail → stop.
2. `SETNX alert:cooldown:{alert_id}` — fail → stop.
3. `SETNX dedup:alert-eval:{alert_id}:{source_event_id}` — fail → stop (**chống Kafka replay**).
4. Publish `alert-triggers` với `source_event_id` + `trigger_fingerprint` — **INV-E01**.

**Cấm:** Gửi FCM/APNs trực tiếp — thuộc SVC-06.

---

### SVC-05: WebSocket Gateway

| | |
|---|---|
| **Input** | Kafka `ticks`, `index-updates`, `flow-updates` |
| **Output** | WSS messages Contract §4.3 |
| **State** | `ChannelRegistry` in-memory — **INV-WSS** |
| **Batching** | 200ms window, latest-only per ticker |

**Lifecycle:** JWT validate on connect → subscribe validates tier → registry mutate → on disconnect purge all conn channels.

**Cấm:** Query Redis/DB. Fanout `alert-triggers`.

---

### SVC-06: Notification Service

| | |
|---|---|
| **Input** | `alert-triggers` |
| **Output** | FCM, APNs, Web Push, email fallback |

**Enforcement**

1. Validate `schema_version`, required `data` fields — **INV-SCH**.
2. `SETNX dedup:alert-trigger:{alert_id}:{session_date}` — duplicate → ack offset, no send — **INV-E01**.
3. Log delivery với `process_time` (Contract §11 event time rule).
