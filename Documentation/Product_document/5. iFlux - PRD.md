## GIẢI THÍCH THUẬT NGỮ

| Thuật ngữ | Nghĩa tiếng Việt | Giải thích trong ngữ cảnh PRD |
|---|---|---|
| **PRD** (Product Requirements Document) | Tài liệu yêu cầu sản phẩm | Tài liệu chuyển hoá yêu cầu nghiệp vụ (BRD) thành yêu cầu chức năng và phi chức năng cụ thể để team build. |
| **FR** (Functional Requirement) | Yêu cầu chức năng | Hệ thống phải làm gì — hành vi, tính năng, luồng xử lý cụ thể. |
| **NFR** (Non-Functional Requirement) | Yêu cầu phi chức năng | Hệ thống phải đáp ứng tiêu chuẩn gì — hiệu năng, bảo mật, khả năng mở rộng. |
| **AC** (Acceptance Criteria) | Tiêu chí chấp nhận | Điều kiện cụ thể, đo được, để xác định tính năng đã hoàn chỉnh hay chưa. |
| **BDD** (Behavior-Driven Development) | Phát triển hướng hành vi | Format viết AC theo cấu trúc: Cho rằng / Khi / Thì. |
| **P0 / P1 / P2** | Mức độ ưu tiên | P0 = Must-have (không có thì không launch), P1 = Should-have, P2 = Nice-to-have. |
| **SCR** | Mã màn hình | Định danh màn hình trong IA. Ví dụ: SCR-011 = Chi tiết Cổ phiếu. |
| **WGT** | Mã Widget | Định danh Widget trong Widget Registry. |
| **BR** | Business Rule | Quy tắc nghiệp vụ từ BRD — PRD kế thừa và mở rộng thành AC. |
| **Synthetic Index** | Chỉ số tổng hợp | Chỉ số OHLCV tính theo vốn hóa cho Ngành/Họ — xem BRD §7. |
| **Paywall** | Rào cản trả phí | Màn hình chặn tính năng Premium đối với người dùng Free. |
| **Deep Link** | Liên kết sâu | URL dẫn trực tiếp vào màn hình cụ thể trong app. |
| **Sticker** | Nhãn ngữ cảnh | Nhãn trạng thái Ngành/Họ hiển thị trong Watchlist — xem BRD §11. |
| **Real-time** | Thời gian thực | Dữ liệu cập nhật liên tục trong phiên, độ trễ ≤ 3 giây. |
| **Delayed** | Dữ liệu chậm | Dữ liệu trễ 15 phút — áp dụng cho người dùng Free ở một số tính năng. |
| **p95** | Phân vị 95 | 95% request phải đáp ứng ngưỡng hiệu năng định nghĩa — chuẩn đo NFR. |
| **WEB-XXX** | Mã trang Website | Định danh trang trên trình duyệt — tương đương SCR trên app (IA §1.5). |
| **ADM-XXX** | Mã màn hình Admin | Định danh màn hình bảng quản trị nội bộ — chỉ nhân viên vận hành. |
| **Platform Parity** | Parity đa nền tảng | App và Web cùng Shared Market Truth và nghiệp vụ cốt lõi — khác trình bày/trọng tâm (BRD §19.1). |
| **Trọng tâm nền tảng** | — | Vai trò ưu tiên App/Web trong hành trình — **không** đồng nghĩa ít tính năng hơn. |
| **Decision Cockpit** | Buồng lái quyết định | Trọng tâm App — Alert Push, Watchlist sâu, Dashboard Widget, Affiliate. |
| **Discovery / Acquisition** | Khám phá / Thu hút user | Trọng tâm Web — SEO, landing, funnel, CTA tải app/đăng ký. |
| **Shared Market Truth** | Sự thật thị trường dùng chung | Cùng API/dữ liệu nghiệp vụ trên App và Web — nền tảng Platform Parity. |
| **SEE / UNDERSTAND / ACT / PERSONALIZE** | Hành trình user | Map Lớp 1–4 Vision (THẤY/HIỂU/HÀNH/CÁ NHÂN HÓA) — BRD §19.6. |
| **Bridge (Bridge layer)** | Cầu nối Web → App | QR, Public Link, Universal Link, WEB-SHR — BR-BRIDGE-01..04. |
| **CTA** (Call-to-Action) | Lời kêu gọi hành động | Nút/link: Đăng ký, Tải app, Theo dõi, Nâng cấp. |
| **Universal Link** | Liên kết mở app | URL `https://...` — đã cài app mở SCR; chưa cài xem web. |

| **Degraded Mode** | Chế độ suy giảm | Mất/chậm nguồn dữ liệu — cache + banner; không hiển thị số giả — BRD §22.3. |
| **Observability** | Khả năng quan sát hệ thống | Đo và kiểm chứng SLA, metric kinh doanh, sức khỏe vận hành — BRD Ch.21. |

| **Alert Hệ thống / Alert Thông minh** | Cảnh báo hệ thống / user | Hệ thống: Admin gửi (ADM-OPS-004); Thông minh: user tự đặt. |

| **Cross-platform Sync** | Đồng bộ đa nền tảng | Cùng tài khoản — Watchlist/Alert/gói thay đổi ở App hoặc Web cập nhật sang nền tảng kia. |
| **Taxonomy Management** | Quản trị phân loại | Admin quản lý mapping Stock ↔ Sector ↔ Ecosystem — nguồn Context Layer và Sticker. |
| **Product KPI** | Chỉ số hiệu quả sản phẩm | Metric kinh doanh (DAU, MRR, Share count…) — BRD Ch.21 L1; xem ADM-OPS-002. |
| **Web-first Sharing** | Chia sẻ ưu tiên Web | Mọi share mở WEB-SHR/public trước; App là bước tùy chọn — BR-BRIDGE-01. |
| **Canonical URL** | URL chuẩn SEO | Thẻ `<link rel="canonical">` — tránh duplicate content khi cùng entity nhiều path. |
| **Go-live Gate** | Cổng phát hành | Điều kiện bắt buộc pass trước Go-live — PEP §6 checklist (GL-xx). |
| **Behavioral Contract** | Cam kết hành vi nghiệp vụ | Quy tắc cách hệ thống cư xử — BRD Ch.22; PRD mở thành AC đo được. |

## 1. Mục đích & SoT

### 1.1 Mục đích

PRD này chuyển hoá yêu cầu nghiệp vụ từ BRD thành **yêu cầu chức năng và phi chức năng cụ thể** để Product Designer, Engineering và QA có thể thực thi. Mỗi yêu cầu đều có Acceptance Criteria đo được.

### 1.2 Nguồn SoT

| Tài liệu | Vai trò | Thứ tự ưu tiên |
|---|---|---|
| **iFlux — BRD v2.1** | SoT chính — mọi FR/NFR phải trace về đây | 1 |
| **iFlux — IA v1.4** | SoT thứ hai — màn hình/trang, navigation, luồng App↔Web↔Admin | 2 |
| **iFlux — Product Vision** | Tham khảo triết lý và trải nghiệm | 3 |

**Quy tắc xử lý conflict giữa tài liệu:**

| Tình huống | Quy tắc |
|---|---|
| BRD và PRD mâu thuẫn về nghiệp vụ | BRD thắng. PRD phải được cập nhật. |
| IA và PRD mâu thuẫn về màn hình/navigation | IA thắng. Nếu cần thay đổi, phải sửa IA trước, sau đó mới sửa PRD. |
| PRD cần chi tiết kỹ thuật mà BRD/IA chưa có | Ghi vào Phần 16 (Câu hỏi còn mở) — không tự quyết định. |
| Data/logic không rõ trong quá trình build | Fallback authority: PM → BRD → OQ log. Không tự giả định. |
| PRD và Tech Spec (khi có) mâu thuẫn | PRD định nghĩa *what*, Tech Spec định nghĩa *how*. Nếu mâu thuẫn về outcome, PRD thắng. |

### 1.3 Phân biệt với BRD và IA

| Tài liệu | Trả lời câu hỏi | Đối tượng |
|---|---|---|
| BRD | *Tại sao* và *Cái gì* (nghiệp vụ) | Stakeholder, Investor |
| IA | *Ở đâu* (cấu trúc điều hướng, màn hình/trang App/Web/Admin) | Designer, PM |
| **PRD** | ***Như thế nào*** (chức năng, tiêu chí đo được) | **Engineering, QA, Designer** |

PRD GĐ1 bao phủ **ba kênh triển khai:** Mobile App (Epic 02–10), Website (Epic 11), Admin + Observability (Epic 12–13) — cùng backend Epic 01.

### 2.4 MVP Definition — Go-live v1.0

> **P0 ≠ MVP.** Toàn bộ P0 là điều kiện cần. MVP là tập con tối thiểu đủ để người dùng thực sự trải nghiệm giá trị cốt lõi của iFlux.

**Tiêu chí xác định MVP:** Người dùng phải có thể thực hiện trọn vẹn "Golden Path" trên **App hoặc Web** — từ khám phá thị trường → xem ngành/họ/mã → thêm Watchlist → nhận Alert — và đội vận hành phải **đo được SLA** qua Admin.

### 2.6 Platform Model — Trọng tâm vs Parity

> **Nguồn SoT:** BRD §1.2, §19.1, §19.6, §19.7; IA §1.4, §15.4, §19

**Nguyên tắc bắt buộc:** **Platform Parity** — App và Web dùng chung **Shared Market Truth** và **nghiệp vụ cốt lõi** (Watchlist, Alert, gói, xem thị trường…) qua **một tài khoản**. Khác nhau ở **trọng tâm trải nghiệm** và cách trình bày — **không** có nghĩa một bên thiếu tính năng nghiệp vụ.

| Platform | Trọng tâm (GĐ 1) | PRD phải đảm bảo |
|---|---|---|
| **Mobile App** | **Decision Cockpit + Action** | Real-time sâu, Push Alert, Dashboard Widget kéo thả, Affiliate Trading |
| **Website** | **Discovery + Narrative + Acquisition** | Public pages SEO, WEB-SHR landing, funnel đăng ký/tải app, Watchlist/Alert web đầy đủ |
| **Admin Panel** | **Governance + Operations** | CMS dữ liệu, quản lý user, **ADM-OPS-001 đo SLA**, audit log |

**Hành trình user — map Vision (SEE → UNDERSTAND → ACT → PERSONALIZE):**

| Lớp | Câu hỏi user | Trọng tâm App | Trọng tâm Web | Parity — **cả hai đều có** |
|---|---|---|---|---|
| **SEE** (THẤY) | Thị trường đang gì? | Real-time sâu, Dashboard | Browse rộng, SEO, public pages | Market, Sector, Ecosystem, Flow, Stock |
| **UNDERSTAND** (HIỂU) | Tại sao? | Context Layer trên SCR | WEB-SHR, narrative, share viral | Context Layer, Insight Card, liên kết thực thể |
| **ACT** (HÀNH ĐỘNG) | Làm gì? | Action Bar, Alert Push, Affiliate | Watchlist/Alert web + **CTA sang app** | Watchlist, Alert, Subscription |
| **PERSONALIZE** (CÁ NHÂN HÓA) | Không gian riêng? | SCR-001 Widget kéo thả | WEB-HOME bố cục cố định | Watchlist, Alert, tier Premium |

**Ngoại lệ parity hợp lệ (không phải thiếu tính năng):**

| Tính năng | App | Web | Lý do |
|---|---|---|---|
| Dashboard Widget kéo thả | ✅ Trọng tâm (SCR-001) | ⚠️ WEB-HOME cố định | Khác **layout** — **không sync** bố cục Widget (BRD §19.2, §22.1) |
| Affiliate Trading | ✅ | ❌ | Ngoại lệ kênh CTCK — BRD §19.2 |
| Push Notification | ✅ Trọng tâm | Browser/email | Khác **kênh thông báo**, cùng điều kiện Alert |
| Landing / SEO public | ❌ | ✅ Trọng tâm | Web-only acquisition |

**Bridge (Web → App):** Mọi share/QR mở **WEB-SHR-001 hoặc trang public** trước (BR-BRIDGE-01, BR-PLAT-05). Universal Link: đã cài app → SCR; chưa cài → web (BR-BRIDGE-03). Chi tiết màn hình: IA §16.6.

**Behavioral Contracts → AC:** Cam kết BRD Ch.22 (BR-CON-01..08) được PRD chuyển thành NFR-PLAT và AC trong Epic 08, 09, 11.

### 5.2 Synthetic Index Engine (F01.02)

**Mô tả:** Tính toán chỉ số OHLCV tổng hợp (Synthetic Index) cho từng Ngành và từng Họ cổ phiếu — nền tảng của tính năng Candlestick Chart nhóm.

**Công thức nghiệp vụ (từ BRD §7.4):**
- **Ig (điểm chỉ số)** = Σ(Giá_i × Số_cổ_phiếu_i) / Divisor
- **Pg (hiệu suất nhóm)** = Trung bình cộng % thay đổi của tất cả mã thành viên
- **OHLCV nhóm**: Open/High/Low/Close lấy từ Ig tại các mốc thời gian tương ứng của khung đang xem

**Yêu cầu chức năng:**

| Mã FR | Yêu cầu | Ưu tiên |
|---|---|---|
| FR-01.02.1 | Tính toán Ig theo Market Cap Weighted cho từng Sector | P0 |
| FR-01.02.2 | Tính toán Ig theo Market Cap Weighted cho từng Ecosystem | P0 |
| FR-01.02.3 | Cập nhật Ig và sinh OHLCV nhóm theo thời gian thực trong phiên | P0 |
| FR-01.02.4 | Lưu trữ lịch sử Ig theo các khung thời gian (1D, 1W, 1M, 3M, 1Y) để hiển thị chart lịch sử | P0 |
| FR-01.02.5 | Tự động tính lại Ig khi Admin thêm/xóa mã trong Sector hoặc Ecosystem | P0 |

**Acceptance Criteria:**

- **AC-01.02.1:** Cho rằng Sector Ngân hàng có 30 mã thành viên. Khi tính Ig tại thời điểm T. Thì Ig phải bằng tổng (Giá_i × Cổ_phiếu_lưu_hành_i) chia cho Divisor — sai số ≤ 0.01%.
- **AC-01.02.2:** Cho rằng Admin thêm mã mới vào Ecosystem. Khi lưu thay đổi. Thì Ig mới phải được tính lại và phản ánh trên app trong vòng 5 phút.

### 5.3 Money Flow Processor — 4 nhóm chủ thể (F01.03)

**Mô tả:** Phân loại và tổng hợp dòng tiền theo 4 nhóm chủ thể trên mọi cấp độ thực thể.

**Định nghĩa 4 nhóm chủ thể (canonical — từ BRD §8.3):**

| Tên hiển thị | Tên kỹ thuật | Nguồn dữ liệu |
|---|---|---|
| Khối ngoại | `foreign` | Tài khoản đăng ký với mã nhà đầu tư nước ngoài (FEID) |
| Tự doanh | `proprietary` | Tài khoản tự doanh của các CTCK (mã tự doanh) |
| Tổ chức nội | `institutional` | Quỹ đầu tư, công ty bảo hiểm, ngân hàng thương mại trong nước |
| Cá nhân | `retail` | Tất cả tài khoản còn lại |

**Yêu cầu chức năng:**

| Mã FR | Yêu cầu | Ưu tiên |
|---|---|---|
| FR-01.03.1 | Phân loại từng lệnh khớp vào đúng nhóm chủ thể dựa trên metadata tài khoản | P0 |
| FR-01.03.2 | Tính toán Mua ròng (Net Buy) = Giá trị Mua − Giá trị Bán cho từng nhóm, theo từng mã | P0 |
| FR-01.03.3 | Tổng hợp Net Buy của nhóm lên cấp Sector = Σ Net Buy của tất cả mã trong Sector | P0 |
| FR-01.03.4 | Tổng hợp Net Buy của nhóm lên cấp Ecosystem tương tự Sector | P0 |
| FR-01.03.5 | Reset và tích luỹ theo phiên — dữ liệu phiên hôm nay và lịch sử theo ngày | P0 |

**Acceptance Criteria:**

- **AC-01.03.1:** Cho rằng một lệnh mua 1 tỷ đồng HPG từ tài khoản nước ngoài khớp thành công. Khi hệ thống xử lý. Thì Net Buy của nhóm `foreign` tại HPG phải tăng thêm đúng 1 tỷ đồng trong vòng 3 giây.
- **AC-01.03.2:** Cho rằng Sector Ngân hàng có 30 mã với Net Buy foreign lần lượt là X₁...X₃₀. Khi tổng hợp. Thì Net Buy foreign của Sector Ngân hàng = Σ(X₁...X₃₀).

### 12.3 Alert Center — SCR-002 (F08.03)

**Nguyên tắc 3 điểm vòng đời Alert (từ IA §8 SCR-002):**
- **Create:** Tạo tại SCR-011, SCR-010, SCR-006, SCR-008
- **Manage:** Chỉ tại SCR-002
- **Trigger:** Push Notification → Deep Link

**Alert Lifecycle — State Machine:**

```
                    [Người dùng tạo Alert]
                            │
                            ▼
                       ┌─────────┐
                       │ CREATED │
                       └────┬────┘
                            │ Lưu thành công
                            ▼
                       ┌────────┐
              ┌────────│ ACTIVE │────────┐
              │        └────────┘        │
              │ Người dùng tắt           │ Điều kiện xảy ra
              ▼                          ▼
         ┌──────────┐             ┌───────────┐
         │ DISABLED │             │ TRIGGERED │
         └────┬─────┘             └─────┬─────┘
              │ Người dùng bật lại      │ Alert vẫn tồn tại
              └──────────┬──────────────┘ (không tự xóa)
                         │
                    [ACTIVE trở lại]
                         
              Ở bất kỳ state nào:
              Người dùng xóa → DELETED (không khôi phục)
```

**Quy tắc state:**
- Alert ở trạng thái **DISABLED** không monitor điều kiện — không tốn tài nguyên.
- Alert ở trạng thái **TRIGGERED** vẫn tiếp tục monitor — sẽ trigger lại nếu điều kiện xảy ra lần sau (trừ khi user tắt).
