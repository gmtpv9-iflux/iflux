### 2.3 Lý do chọn kiến trúc này

- **Kafka làm message bus:** Tách data ingestion khỏi processing engine — khi Data Provider gián đoạn, Kafka buffer đảm bảo không mất tick. Các engine đọc từ Kafka độc lập nhau, có thể scale riêng.
- **TimescaleDB cho time-series:** OHLCV data có tính chất time-series điển hình — TimescaleDB (extension trên PostgreSQL) cho phép time_bucket(), compression policy tự động, và tương thích hoàn toàn với PostgreSQL ecosystem.
- **Redis cho real-time cache:** Ig hiện tại, top ranking, và trạng thái Contextual Sticker cần truy xuất < 10ms — Redis với ZSET/HASH là lựa chọn tự nhiên.
- **WebSocket cho App real-time push:** Mobile client không poll — server push khi có update. **Web** dùng REST refresh ~30s (NFR-PLAT-05) — không mở WebSocket full market fanout cho browser.
- **Web BFF tách khỏi Market Service:** SSR và SEO logic không nằm trong engine — tránh coupling product presentation với computation.
- **Platform Sync qua Kafka `user-events`:** Cross-platform invalidation tách biệt khỏi Alert Engine — §24.4.

### 3.6 Entity ID Convention (Chuẩn hoá `entity_id`)

> **Vấn đề:** `entity_type` và `entity_id` xuất hiện trong nhiều bảng (`money_flow`, `alerts`, `large_lots`) nhưng có mixed typing: Stock dùng `VARCHAR(ticker)`, Sector/Ecosystem dùng `INT(id)`. Nếu không chuẩn hoá, JOIN và query sẽ không nhất quán.

| entity_type | entity_id format                | Ví dụ                 |
| ----------- | ------------------------------- | --------------------- |
| `stock`     | Ticker trực tiếp (uppercase)    | `"HPG"`, `"VIC"`      |

| `ecosystem` | Tiền tố `"eco:"` + ecosystem.id | `"eco:7"`, `"eco:3"`  |


**Lý do chọn Option A (TEXT + prefix) thay vì BIGINT:**

- Không cần mapping table bổ sung
- Human-readable trong log và debug
- Redis key đã dùng pattern này → nhất quán
- Đánh đổi: không có FK constraint native — phải validate ở application layer

**Áp dụng lại cho bảng `alerts` (sửa comment):**

```sql

-- stock: "HPG" | sector: "sec:5" | ecosystem: "eco:7"
```

### 4.2.1 Backpressure & Retry Strategy

**Vấn đề:** Tick burst trong giờ cao điểm (đầu phiên 9:00, ATC 14:30–15:00) có thể tạo consumer lag → mất real-time SLA.

**Retry policy cho consumer (Synthetic Index + Money Flow Engine):**

```
On message processing failure:

Attempt 1 (immediate):
    Process tick normally
    ├── SUCCESS → commit offset
    └── FAIL (transient error: Redis timeout, compute error)
            → publish to "ticks.retry.1s" with retry_count=1
            → commit offset (không block main consumer)

Attempt 2 (sau 1 giây, từ retry.1s topic):
    Re-process tick
    ├── SUCCESS → done
    └── FAIL → publish to "ticks.retry.30s" with retry_count=2

Attempt 3 (sau 30 giây, từ retry.30s topic):
    Re-process tick
    ├── SUCCESS → done
    └── FAIL → publish to "ticks.dlq" with error_reason
              → Slack alert gửi về #engineering-alerts
```

**Consumer lag monitoring:**

```
Nếu consumer lag của "ticks" topic > 500ms (tức ~N messages chưa xử lý):
    → Slack alert: "Tick processing lag: {lag}ms"
    
Nếu lag > 2s:
    → PagerDuty: "CRITICAL — Real-time SLA at risk"
    → Auto-scale thêm consumer instance nếu có
```

**Burst handling:** Kafka partition được cấu hình theo ticker hash → mỗi ticker luôn được xử lý bởi cùng 1 consumer instance → đảm bảo ordering per-ticker.

### 4.3 Event Standard Envelope & Money Flow Definition of Truth

#### 4.3.1 Event Envelope chuẩn (áp dụng toàn bộ Kafka topics)

Mọi message trên mọi Kafka topic đều phải bọc trong envelope sau. `data` chứa payload riêng của từng event type.

```json
{
  "event_id":       "uuid-v4",
  "event_type":     "TICK | INDEX_UPDATE | FLOW_UPDATE | ALERT_TRIGGER | ECOSYSTEM_CHANGED",
  "event_time":     "2026-06-21T09:15:32.123Z",
  "process_time":   "2026-06-21T09:15:32.187Z",
  "source":         "data-ingestion",
  "schema_version": "v1",
  "data":           { ... }
}
```

**Quy tắc versioning:**

- `schema_version` tăng khi có **breaking change** (xóa field, đổi type).
- Thêm field mới (non-breaking) → không tăng version, consumer phải ignore unknown fields.
- Consumer phải check `schema_version` và từ chối nếu không support → gửi vào DLQ kèm reason.

**Backward compatibility rule:**

```
Producer (new schema) → Consumer (old schema): Consumer MUST ignore unknown fields.
Producer (old schema) → Consumer (new schema): Consumer MUST handle missing optional fields with defaults.
Breaking change: tăng schema_version + deploy consumer trước producer.
```

#### 4.3.3 Money Flow — Definition of Truth

> **Câu chốt bắt buộc:** iFlux dùng **tick-based approximation** cho Money Flow — không dùng order-book-based truth.

**Lý do chọn tick-based:**

- Data Provider cung cấp tick data (matched trades), không cung cấp full order book
- Tick-based đủ chính xác cho mục đích phân tích dòng tiền (precision ~95-98% so với order-book-based)
- Order-book-based yêu cầu kết nối L2 market data — chi phí cao hơn nhiều

**Hệ quả phải accept:**

- Active Buy/Sell là **xấp xỉ** dựa trên so sánh `price` với `bid_price`/`ask_price` tại thời điểm tick
- Một số lệnh khớp giữa chừng sẽ không được phân loại (is_active = false) → loại khỏi Active Flow
- Net Flow tổng vẫn chính xác 100% (mọi lệnh đều được tính vào buy_value hoặc sell_value)

**Logic phân loại Active Buy / Active Sell:**

- Nếu `price >= ask_price` → `is_active = true`, `side = BUY` → Active Buy
- Nếu `price <= bid_price` → `is_active = true`, `side = SELL` → Active Sell
- Còn lại: `is_active = false` (lệnh khớp giữa chừng — không tính vào Active Flow, vẫn tính vào Net Flow)

**Logic phân loại Chủ thể:** Được thực hiện tại Data Ingestion Service dựa trên metadata tài khoản từ Data Provider (field code `subject`):

- Có FEID → `subject = "foreign"`
- Có mã tự doanh CTCK → `subject = "proprietary"`
- Có mã tổ chức (quỹ, bảo hiểm, ngân hàng) → `subject = "institutional"`
- Còn lại → `subject = "retail"`

## 5. Synthetic Index Engine

### 5.1 Thuật toán tính Ig

**Input:** Tick message từ Kafka topic `ticks`  
**Output:** Publish `index-updates` message + Write to Redis + Async write to `group_index_ohlcv`

```
On receive tick(ticker, price, volume, sector_id, ecosystem_id):

1. UPDATE in Redis:
   - HSET "stock:HPG" price=27800 shares=4500000000
   
2. COMPUTE Ig for Sector:
   sector_members = SMEMBERS "sector:{sector_id}:members"
   Ig = Σ(price_i × shares_i) / divisor
   Pg = mean([(price_i - ref_price_i) / ref_price_i] for each member)
   
3. COMPUTE Ig for Ecosystem (if ecosystem_id exists):
   Same formula with ecosystem members
   
4. UPDATE Redis:
   HSET "index:sector:{id}" ig=Ig pg=Pg ts=now()
   HSET "index:ecosystem:{id}" ig=Ig pg=Pg ts=now()
   
5. PUBLISH to Kafka "index-updates":
   { group_type, group_id, ig, pg, breadth_up, breadth_down, ts }
   
6. ASYNC: Upsert into group_index_ohlcv (1m timeframe)
```

### 5.2 Quản lý Divisor

Divisor được điều chỉnh khi:

- Admin thêm/xóa mã khỏi Sector/Ecosystem
- Cổ phiếu phát hành thêm (rights issue)

**Công thức điều chỉnh Divisor khi thêm mã mới:**

```
Divisor_mới = Divisor_cũ × (Ig_trước_thay_đổi + Price_mã_mới × Shares_mã_mới) / Ig_trước_thay_đổi
```

Điều chỉnh này đảm bảo Ig không thay đổi đột ngột khi cơ cấu thành viên thay đổi.

**Quy trình Admin thêm mã:**

1. Admin submit thay đổi trong CMS
2. System tính Divisor mới
3. Admin preview: "Ig sẽ thay đổi từ X → Y (0.00%)" để confirm
4. Admin confirm → System cập nhật Divisor trong `sectors`/`ecosystems`
5. Publish event lên Kafka để Synthetic Index Engine reload config từ DB
6. Hiệu lực ngay lập tức trong ≤ 5 phút (SLA từ PRD FR-01.05.3)

### 5.3 Edge Cases trong Synthetic Index

Các trường hợp đặc biệt phải được xử lý đúng để tránh Ig bị spike hoặc tính sai:

#### EC-01: Cổ phiếu IPO chưa có ref_price

```
Vấn đề: Pg tính bằng (price - ref_price) / ref_price
         → nếu ref_price = 0 hoặc NULL → divide by zero

Giải pháp:
    - Ngày đầu tiên giao dịch: ref_price = giá khớp đầu tiên của phiên
    - Pg của mã IPO trong phiên đầu tiên = 0 (không đưa vào tính Pg nhóm)
    - Ig vẫn tính bình thường (chỉ cần price và shares)
    - Từ phiên thứ 2 trở đi: ref_price = giá đóng cửa phiên trước → bình thường
```

#### EC-02: Cổ phiếu bị tạm dừng giao dịch (Suspended / Halted)

```
Vấn đề: Khi cổ phiếu bị halt, không có tick mới
         → Ig vẫn dùng giá cũ → OK về logic
         → Breadth counting: mã halt không tính vào advance/decline

Giải pháp:
    - Data Ingestion nhận tín hiệu halt từ Data Provider
    - HSET stock:{ticker} status=halted
    - Synthetic Index Engine: khi tính breadth, skip mã halted
    - Ig vẫn dùng giá cuối cùng trước halt → không thay đổi → OK
    - Hiển thị trên app: mã halted có icon cảnh báo riêng
```

#### EC-03: shares_outstanding update delay (phát hành thêm cổ phiếu)

```
Vấn đề: Khi công ty phát hành thêm (rights issue, ESOP, bonding),
         shares_outstanding thay đổi nhưng Data Provider có thể cung cấp trễ 1-2 ngày
         → Ig bị sai trong thời gian delay

Giải pháp:
    - Admin CMS có tính năng cập nhật shares_outstanding thủ công kèm effective_date
    - Batch job đêm đồng bộ shares từ nguồn chính thức (HOSE disclosure)
    - Khi shares thay đổi → tính lại Divisor theo §5.2 → không gây Ig spike
    - Log mọi thay đổi shares vào audit table để traceability
```

#### EC-04: Nhóm chỉ có 1 mã thành viên

```
Vấn đề: Ecosystem nhỏ có thể chỉ có 1 mã → Ig = giá × shares / divisor
         → về lý thuyết đúng, nhưng gây hiểu lầm (Ig = "chỉ số" của 1 mã?)

Giải pháp:
    - Minimum 2 mã thành viên để hiển thị Candlestick Chart nhóm
    - Nếu < 2 mã: hiển thị danh sách thành viên thay vì chart
    - Admin CMS enforce rule này khi tạo Ecosystem mới
```

### 5.4 Redis Key Structure cho Synthetic Index

```
stock:{ticker}              HASH  { price, shares, ref_price, sector_id, ecosystem_id }
sector:{id}:members         SET   { "HPG", "HSG", "NKG", ... }
ecosystem:{id}:members      SET   { "VIC", "VHM", "VRE", ... }
index:sector:{id}           HASH  { ig, pg, breadth_up, breadth_down, breadth_flat, total_value, ts }
index:ecosystem:{id}        HASH  { ig, pg, breadth_up, breadth_down, breadth_flat, total_value, ts }

```

## 6. Money Flow & Large Lots Engine

### 6.1 Money Flow Accumulation (Idempotency & Rebuild)

**Idempotency — Dedup per Consumer:**

Trước khi xử lý bất kỳ tick nào, Money Flow Engine kiểm tra dedup để tránh double-count khi tick bị replay (DLQ retry hoặc Kafka consumer restart):

```go
func processTickIdempotent(tick Tick) error {
    dedupKey := fmt.Sprintf("dedup:flow:%s", tick.EventID)
    
    // SETNX với TTL 24h — chỉ xử lý nếu chưa từng xử lý event này
    set := redis.SetNX(ctx, dedupKey, "1", 24*time.Hour)
    if !set {
        // Đã xử lý rồi — skip (idempotent)
        return nil
    }
    
    return processTick(tick)  // thực hiện INCRBY
}
```

Synthetic Index Engine dùng cùng pattern với key prefix `dedup:index:{event_id}`.

**Logic cập nhật (per tick):**

```
On receive tick(ticker, value, side, is_active, subject, session_date, sector_id, ecosystem_id):

0. DEDUP CHECK (xem §6.1 idempotency trên)

1. Classify:
   buy_value  = value if side=="BUY"  else 0
   sell_value = value if side=="SELL" else 0
   
2. UPDATE Redis (atomic INCRBY):
   Key: flow:{entity_type}:{entity_id}:{subject}:{session_date}
   INCRBY flow:stock:{ticker}:{subject}:{date}:buy  buy_value
   INCRBY flow:stock:{ticker}:{subject}:{date}:sell sell_value
   
3. AGGREGATE to Sector/Ecosystem:
   INCRBY flow:sector:{sector_id}:{subject}:{date}:buy  buy_value
   INCRBY flow:sector:{sector_id}:{subject}:{date}:sell sell_value
   (tương tự cho ecosystem nếu có)
   
4. UPDATE Ranking ZSET:
   net = buy - sell
   ZADD ranking:stock:flow:{date} net {ticker}
   ZADD ranking:sector:flow:{date} sector_net {sector_id}
```

**State Rebuild Strategy (khi Redis mất dữ liệu phiên hiện tại):**

Đây là vấn đề nghiêm trọng — Redis không có dữ liệu phiên nhưng phiên chưa kết thúc nên TimescaleDB chưa có flush. Cần rebuild từ Kafka:

```
Redis restart trong giờ giao dịch:

1. Money Flow Engine detect Redis empty (không có key flow:*:{today})
2. Trigger "state-rebuild" mode:
   a. Xác định earliest_offset = offset của tick đầu tiên của phiên hôm nay trong Kafka
      (dùng Kafka timestamp index, hoặc seek đến 09:00 ICT của ngày hôm nay)
   b. Replay toàn bộ tick từ earliest_offset đến offset hiện tại
   c. TRONG rebuild mode: bật dedup check (event_id) để tránh count tick hai lần
      nếu consumer đã xử lý một số tick trước khi crash
   d. Sau khi replay xong: resume realtime processing bình thường
   
3. WebSocket push "rebuilding" state → client hiển thị spinner nhỏ
4. Rebuild time estimate: ~1 phút cho phiên thông thường (~100k-500k ticks)
```

**End-of-session (16:00):** Persistence Worker đọc từ Redis và ghi xuống `money_flow` table trong TimescaleDB.

### 6.2 Large Lots Engine

```
On receive tick(ticker, value, side, is_active, subject, price, volume):

1. Lookup lot_threshold:
   threshold = HGET stock:{ticker} lot_threshold   -- từ Redis cache
   
2. Check:
   if value >= threshold:
       label as Large Lot
       
3. Store in Redis (timeseries list):
   LPUSH largelot:{ticker}:{date} JSON(tick)
   EXPIRE largelot:{ticker}:{date} 86400  -- 1 ngày
   
4. UPDATE Large Lot Net Flow:
   INCRBY largflow:{ticker}:{date}:buy  value if BUY
   INCRBY largflow:{ticker}:{date}:sell value if SELL
   
5. ASYNC: Insert into large_lots table
```

```
flow:sector:{id}:{subject}:{date}:sell      STRING
flow:ecosystem:{id}:{subject}:{date}:buy    STRING
flow:ecosystem:{id}:{subject}:{date}:sell   STRING
ranking:stock:flow:{date}                   ZSET    (ticker → net_flow)
ranking:sector:flow:{date}                  ZSET    (sector_id → net_flow)
```

### 8.1.1 Fanout Architecture, Channel Registry & Throttling

**Vấn đề:** 10,000 connections/instance nhưng không phải mọi client đều subscribe cùng channel. Cần routing hiệu quả — không broadcast tất cả cho tất cả.

```
Kafka topic: index-updates, flow-updates, ticks
        │
        ▼
WebSocket Gateway (không query DB, chỉ consume Kafka)
        │
        ├── Channel Registry (in-memory):
        │   { "stock:HPG": [conn_1, conn_5, conn_23, ...],
        │     "index:sector:5": [conn_2, conn_7, ...],
        │     "flow:sector:5:foreign": [conn_3, ...] }
        │
        ├── On Kafka message received:
        │   channel = derive_channel(message)
        │   conns   = registry[channel]
        │   for conn in conns: conn.send(message)
        │
        └── Constraint: WebSocket Gateway KHÔNG trực tiếp query DB hay Redis
            → chỉ fan-out Kafka messages đến đúng subscribers
```

**Multi-instance fanout:** Mỗi WebSocket Gateway instance có Channel Registry riêng. Kafka consumer group đảm bảo mỗi message được consume bởi ít nhất 1 instance.

**Throttling — Batching Window (chống spam client khi high volatility):**

```go
// Mỗi channel có 1 batching buffer, flush mỗi 200ms
type ChannelBuffer struct {
    latestMsg map[string]Message  // only keep latest per ticker
    mu        sync.Mutex
}

func (b *ChannelBuffer) Put(ticker string, msg Message) {
    b.mu.Lock()
    b.latestMsg[ticker] = msg  // overwrite — drop intermediate updates
    b.mu.Unlock()
}

// Ticker goroutine: flush mỗi 200ms
func (b *ChannelBuffer) Flush(conns []Conn) {
    b.mu.Lock()
    msgs := b.latestMsg
    b.latestMsg = make(map[string]Message)
    b.mu.Unlock()
    
    for _, msg := range msgs {
        for _, conn := range conns { conn.send(msg) }
    }
}
```

**Drop policy:** Chỉ giữ giá trị mới nhất mỗi ticker trong mỗi window 200ms. Client nhận được price update cuối nhất, không nhận được mọi tick trung gian — phù hợp với display use case.

**Per-connection subscription limits (Hard Limits — xem §21):**

- Max 50 channels per connection
- Vượt giới hạn → server từ chối subscribe và gửi error message

### 9.2 Alert Matching — Inverted Index

**Vấn đề với naive loop:** O(N alerts) per tick. Khi có 100k active alerts và 10k ticks/phiên → 1 tỷ operations/phiên → không scale.

**Giải pháp: Inverted Index theo entity + field type**

```
Cấu trúc in-memory (Go map):

alert_index = {
    "stock:HPG:price":       [alert_id_1, alert_id_5, alert_id_23],
    "stock:HPG:net_flow":    [alert_id_7],
    "sector:sec:5:rank":     [alert_id_12, alert_id_44],
    "ecosystem:eco:7:pg":    [alert_id_3],
}

alert_store = {
    alert_id_1: Alert{ conditions: [...], user_id: ..., type: ... },
    ...
}
```

**Match algorithm với inverted index:**

```go
func matchAlerts(event Event) []Alert {
    // O(1) lookup thay vì O(N)
    keys := buildIndexKeys(event)  // VD: ["stock:HPG:price", "stock:HPG:net_flow"]
    
    triggered := []Alert{}
    seen := map[int64]bool{}
    
    for _, key := range keys {
        alertIDs := alertIndex[key]  // lookup O(1)
        for _, id := range alertIDs {
            if seen[id] { continue }
            seen[id] = true
            
            alert := alertStore[id]
            if checkAllConditions(alert.Conditions, event) {
                triggered = append(triggered, alert)
            }
        }
    }
    return triggered
}

func buildIndexKeys(event Event) []string {
    keys := []string{
        fmt.Sprintf("%s:%s:price",    event.EntityType, event.EntityID),
        fmt.Sprintf("%s:%s:volume",   event.EntityType, event.EntityID),
        fmt.Sprintf("%s:%s:net_flow", event.EntityType, event.EntityID),
        fmt.Sprintf("%s:%s:rank",     event.EntityType, event.EntityID),
    }
    return keys
}
```

**Complexity:** O(K) trong đó K = số alerts trên entity đó (thường << 100) thay vì O(N tổng tất cả alerts).

**Index management:**

```go
// Khi user tạo alert mới:
func addAlert(alert Alert) {
    alertStore[alert.ID] = alert
    for _, cond := range alert.Conditions {
        key := fmt.Sprintf("%s:%s:%s", alert.EntityType, alert.EntityID, cond.Field)
        alertIndex[key] = append(alertIndex[key], alert.ID)
    }
}

// Khi user xóa/disable alert:
func removeAlert(alertID int64) {
    alert := alertStore[alertID]
    for _, cond := range alert.Conditions {
        key := fmt.Sprintf("%s:%s:%s", alert.EntityType, alert.EntityID, cond.Field)
        alertIndex[key] = removeFromSlice(alertIndex[key], alertID)
    }
    delete(alertStore, alertID)
}
```

**Reload on start:** Load toàn bộ active alerts từ DB vào in-memory index khi service khởi động. Dùng PostgreSQL LISTEN/NOTIFY để cập nhật incremental khi có thay đổi.

### 9.4 Alert Cooldown & Deduplication

**Vấn đề:** Alert match mỗi tick → nếu giá dao động quanh ngưỡng Alert, có thể trigger hàng chục notification trong vài phút → spam user.

**Cooldown per Alert:**

```go
func shouldTrigger(alert Alert, eventTime time.Time) bool {
    cooldownKey := fmt.Sprintf("alert:cooldown:%d", alert.ID)
    
    // Mặc định cooldown 60 giây; Alert type Ranking/Group dùng 300 giây
    ttl := 60 * time.Second
    if alert.Type == "ranking" || alert.Type == "group" {
        ttl = 300 * time.Second
    }
    
    // Chỉ trigger nếu chưa trigger trong TTL
    set := redis.SetNX(ctx, cooldownKey, eventTime.Unix(), ttl)
    return set  // true = được trigger, false = còn trong cooldown
}
```

**Idempotency key per trigger:**

Khi Notification Service nhận message từ Kafka `alert-triggers`, kiểm tra dedup:

```go
dedupKey := fmt.Sprintf("dedup:alert-trigger:%d:%s", alertID, sessionDate)
if !redis.SetNX(ctx, dedupKey, "1", 24*time.Hour) {
    return nil  // đã gửi notification này rồi
}
sendPushNotification(...)
```

| **C3 — Analytical**     | 30s–5 phút | Candle lịch sử (1D+), Sector/Ecosystem detail (không phải real-time field), API response aggregate | Timed expiry; invalidate khi Admin đổi cấu hình |

## 16. Failure Mode Design

> **Nguyên tắc:** Mọi failure mode phải có hành vi xác định — không được để hệ thống ở trạng thái undefined. Mỗi kịch bản đều có: detection, response, user impact, và recovery.

### 16.1 Data Provider mất kết nối

```
Detection:
    Data Ingestion Service không nhận được tick trong 10 giây → trigger circuit breaker

Response:
    1. Data Ingestion publish message "feed-degraded" lên Kafka topic "system-events"
    2. API Gateway nhận event → set flag "degraded_mode=true" trong Redis
    3. Mọi API response thêm header: X-Data-Status: degraded + field "data_as_of": timestamp
    4. App client đọc flag → hiển thị banner "Dữ liệu có thể chưa cập nhật"
    5. WebSocket Gateway dừng push real-time updates (không push stale data)

User impact:
    - Dữ liệu đóng băng tại thời điểm cuối cùng nhận được
    - Ranking, Ig, Flow không cập nhật
    - Chart lịch sử (1D+) vẫn hoạt động bình thường (từ TimescaleDB)

Recovery:
    - Khi feed khôi phục → Data Ingestion publish "feed-restored"
    - API Gateway xóa flag degraded
    - Các engine tự động tiếp tục từ tick mới nhất
    - Không cần manual intervention
    
SLA: Phát hiện mất feed trong ≤ 30 giây. Banner xuất hiện trên app trong ≤ 35 giây.
```

### 16.2 Kafka cluster down

```
Detection:
    Producer timeout khi publish tick → alert ngay

Response:
    Data Ingestion Service: switch sang local buffer (in-memory ring buffer, max 60 giây ticks)
    
    Nếu Kafka khôi phục trong 60 giây:
        Flush buffer → publish backlog (ordered) → tiếp tục bình thường
        
    Nếu Kafka down > 60 giây:
        Buffer overflow → Data Ingestion publish "kafka-down" → trigger PagerDuty
        Hệ thống vào degraded mode (như §16.1)
        Không mất dữ liệu nếu recovery trong 60 giây

Recovery:
    Sau khi Kafka online → flush buffer → consumer tự động tiếp tục
    Persistence Worker check missing time ranges và backfill từ Data Provider (nếu có API)
```

### 16.3 Redis restart / data loss

```
Detection:
    Service kết nối Redis fail → immediate alert

Impact:
    - Real-time state (Ig, flow accumulation) mất — KHÔNG thể phục hồi từ Redis
    - Cần rebuild từ nguồn khác

Response:
    1. Synthetic Index Engine: reload Ig từ TimescaleDB (candle gần nhất) → dùng làm baseline
    2. Money Flow Engine: reload flow accumulation từ TimescaleDB (session_date = today) 
       → tích lũy lại từ đó (chấp nhận gap trong khoảng Redis down)
    3. Alert Engine: reload alert index từ PostgreSQL (không mất)
    4. Khoảng thời gian Redis down: flow data có gap — log rõ trong audit table

Recovery time target: ≤ 2 phút từ khi Redis online đến khi Ig và Flow chính xác trở lại.

Phòng ngừa: Redis AOF (Append Only File) persistence + Redis Sentinel cho failover tự động.
```

### 16.4 Synthetic Index Engine crash / restart

```
Detection:
    Health check endpoint /health không response trong 5s → Kubernetes restart container

Response:
    Khi engine khởi động lại:
    1. Load divisor và member lists từ PostgreSQL
    2. Load giá hiện tại của từng stock từ Redis (nếu Redis còn sống)
       HOẶC load từ Data Provider REST API (fallback)
    3. Tính lại Ig từ current prices → cập nhật Redis
    4. Tiếp tục subscribe Kafka từ offset mới nhất (chấp nhận gap nhỏ)
    
Downtime target: ≤ 30 giây (Kubernetes restart + re-init).
```

### 16.5 Bảng tổng hợp Failure Modes


| Failure           | Detection time | User impact           | Recovery                   | Data loss                      |
| ----------------- | -------------- | --------------------- | -------------------------- | ------------------------------ |
| Data Provider mất | ≤ 30s          | Banner + frozen data  | Tự động khi feed khôi phục | Không                          |
| Kafka down < 60s  | Immediate      | Minimal (buffer)      | Tự động + backfill         | Không                          |
| Kafka down > 60s  | 60s            | Degraded mode         | Manual + PagerDuty         | Có thể tick trong period       |
| Redis restart     | Immediate      | Gap trong flow data   | ≤ 2 phút                   | Flow gap = duration Redis down |
| Engine crash      | 5s             | 30s Ig không cập nhật | Kubernetes auto-restart    | Gap nhỏ                        |
| DB Primary down   | Sentinel alert | API errors (writes)   | Replica promote ≤ 30s      | Giao dịch in-flight            |

## 17. Reconciliation & Data Consistency

### 17.1 Redis vs TimescaleDB Reconciliation Job

**Vấn đề:** Persistence Worker ghi Redis → TimescaleDB vào cuối phiên. Nếu Worker fail hoặc Redis restart có gap, TimescaleDB sẽ thiếu data.

**Job: `session-reconciliation`** (chạy lúc 17:00 mỗi ngày giao dịch, sau daily-ohlcv-rollup)

```python
def reconcile_session(session_date):
    # 1. Lấy danh sách tất cả stocks có giao dịch hôm nay từ TimescaleDB
    db_tickers = query_timescale(
        "SELECT DISTINCT ticker FROM stock_ohlcv WHERE session_date = %s", session_date
    )
    
    # 2. So sánh với Data Provider's official trade list (nếu có API)
    provider_tickers = fetch_provider_traded_stocks(session_date)
    
    missing_tickers = provider_tickers - db_tickers
    
    # 3. Với mỗi ticker thiếu: backfill từ Data Provider historical API
    for ticker in missing_tickers:
        raw_data = fetch_provider_history(ticker, session_date)
        insert_timescale(raw_data)
        log_reconciliation_action(ticker, "backfilled", session_date)
    
    # 4. Verify money_flow totals vs large_lots totals
    # (Net flow từ all ticks phải khớp với sum của large_lots net)
    verify_flow_consistency(session_date)
    
    # 5. Alert nếu có inconsistency > threshold
    if inconsistency_count > 0:
        send_alert("Reconciliation found issues", details)
```

### 17.2 Late Ticks (Ticks đến muộn)

**Vấn đề:** Data Provider đôi khi gửi tick muộn (network lag, retry) → tick với `matched_at` thuộc phiên cũ đến vào phiên mới.

**Xử lý:**

```
Data Ingestion Service nhận tick:
    matched_at = tick["matched_at"]
    current_session = get_current_session_date()
    
    if date(matched_at) == current_session:
        → publish to "ticks" → xử lý bình thường
        
    elif date(matched_at) == current_session - 1 day:
        → publish to "ticks.late" (separate topic)
        → Late Tick Processor: update TimescaleDB trực tiếp (bypass Redis accumulation)
        → Log để reconciliation verify
        
    else (older than 1 session):
        → publish to "ticks.dlq" với reason="too_old"
        → Manual review
```

## 18. Time Consistency Rule

### 18.1 Event Time vs Processing Time

**Vấn đề:** Mỗi tick có 2 timestamps khác nhau:

- `matched_at`: thời điểm lệnh khớp trên sàn (event time — source of truth cho dữ liệu)
- `processed_at`: thời điểm hệ thống xử lý tick (processing time — source of truth cho monitoring)

**Quy tắc bất biến:**


| Trường hợp                    | Dùng timestamp nào                | Lý do                                                                   |
| ----------------------------- | --------------------------------- | ----------------------------------------------------------------------- |
| OHLCV candle grouping         | `matched_at`                      | Nến phải reflect thời gian giao dịch thực, không phải thời gian xử lý   |
| Money Flow session assignment | `matched_at` (session_date field) | Flow của một phiên phải bao gồm đúng các lệnh của phiên đó              |
| Consumer lag monitoring       | `processed_at - matched_at`       | Đo độ trễ thực của pipeline                                             |
| Alert trigger timestamp       | `matched_at`                      | Alert triggered "khi điều kiện xảy ra", không phải khi system phát hiện |
| Notification sent timestamp   | `processed_at` (server time)      | Notification delivery là processing event                               |
| Audit log                     | Cả hai                            | Đủ thông tin để debug                                                   |


### 18.2 Time Zone Convention

- **Tất cả timestamp lưu trong DB:** UTC (TIMESTAMPTZ)
- **Tất cả API response timestamp:** UTC, format ISO 8601 (`2026-06-21T09:15:32.123Z`)
- **Display trên app:** UTC+7 (Giờ Việt Nam) — convert tại client, không tại server
- **Session date:** Sử dụng múi giờ Việt Nam (UTC+7) để xác định ngày phiên. `session_date = DATE(matched_at AT TIME ZONE 'Asia/Ho_Chi_Minh')`

### 18.3 Clock Skew Handling

Tick từ Data Provider có thể có `matched_at` lệch giờ nhỏ so với server time do clock skew.

**Rule:**

- Chấp nhận tick có `matched_at` trong khoảng `[server_time - 30s, server_time + 5s]`
- Tick ngoài khoảng này → gửi vào `ticks.dlq` với reason=`clock_skew` + structured log:

```json
{
  "level": "warn",
  "event": "tick_rejected_skew",
  "ticker": "HPG",
  "matched_at": "...",
  "server_time": "...",
  "delta_ms": 45000
}
```

- Metric Prometheus: `iflux_ticks_rejected_skew_total` — hiển thị trên ADM-OPS-006 / Grafana khi spike
- Alert nếu > 10 ticks/phút bị reject vì clock skew (dấu hiệu Data Provider có vấn đề — đối chiếu với Provider log)

## 20. Cache Stampede Protection

**Vấn đề:** Khi cache key expire và 1000 request đồng thời miss → 1000 DB query cùng lúc → DB spike.

**Giải pháp: Single Flight per cache key**

```go
// Dùng golang.org/x/sync/singleflight
var sfGroup singleflight.Group

func getCachedSectorCandles(sectorID int, timeframe string) ([]Candle, error) {
    key := fmt.Sprintf("api:sector:%d:candles:%s", sectorID, timeframe)
    
    result, err, _ := sfGroup.Do(key, func() (interface{}, error) {
        // Chỉ 1 goroutine chạy query này tại một thời điểm
        // Tất cả goroutine khác đang chờ cùng key sẽ nhận result này
        candles, err := queryTimescaleDB(sectorID, timeframe)
        if err != nil { return nil, err }
        
        redis.Set(ctx, key, marshal(candles), 30*time.Second)
        return candles, nil
    })
    
    return result.([]Candle), err
}
```

**Áp dụng cho:** Tất cả cache key thuộc Class C3 (Analytical, 30s+). C1 và C2 không cần vì TTL ngắn + event-driven invalidation.

**Endpoint bắt buộc Single Flight (C3)** — tránh DB spike khi TTL expire đồng loạt hoặc sau restart:


| Endpoint                       | Cache key pattern                 | Ghi chú                |
| ------------------------------ | --------------------------------- | ---------------------- |
| `GET /sectors/{id}/candles`    | `api:sector:{id}:candles:{tf}`    | Query TimescaleDB nặng |
| `GET /ecosystems/{id}/candles` | `api:ecosystem:{id}:candles:{tf}` | Tương tự               |
| `GET /stocks/{ticker}/candles` | `api:stock:{ticker}:candles:{tf}` | Public + authenticated |
| `GET /sectors`                 | `api:sectors:list`                | Ranking lớn            |
| `GET /ecosystems`              | `api:ecosystems:list`             | Ranking lớn            |


Kích hoạt đặc biệt: market open (9:00), post-deploy cache cold start.

## 22. Data Retention & Downsampling Policy

### 22.1 Downsampling Pipeline

```
Raw ticks
    │ Real-time
    ▼
1m OHLCV (stock + group_index)
    │ daily-ohlcv-rollup (16:00)
    ▼
1D OHLCV
    │ weekly-ohlcv-rollup (Thứ 6)
    ▼
1W OHLCV
    │ monthly-ohlcv-rollup (cuối tháng)
    ▼
1M OHLCV
```

Intermediate timeframes 5m, 15m, 1h: **tính on-the-fly từ 1m data** khi có query — không lưu riêng để tiết kiệm storage.

### 22.2 Retention Policy


| Data                   | Lưu ở       | Retention                     | Lý do                                            |
| ---------------------- | ----------- | ----------------------------- | ------------------------------------------------ |
| Raw ticks (Kafka)      | Kafka       | 24 giờ                        | Đủ cho replay intraday; hơn 24h dùng TimescaleDB |
| 1m OHLCV (stock)       | TimescaleDB | 6 tháng → compress sau 7 ngày | Sau 6 tháng downgrade xuống 1D                   |
| 1m group_index         | TimescaleDB | 6 tháng                       | Tương tự                                         |
| 1D OHLCV               | TimescaleDB | Vĩnh viễn                     | Core historical data                             |
| 1W, 1M OHLCV           | TimescaleDB | Vĩnh viễn                     | —                                                |

#### 24.4.1 Conflict Resolution (Optimistic Lock)

> **Map:** NFR-PLAT-01..02; error `SYNC_CONFLICT` §25.8; QA concurrent edit 2 thiết bị.

**Cơ chế:**

- `watchlist_items.version` và `alerts.version` — tăng +1 mỗi mutation thành công
- Client gửi `If-Match: {version}` hoặc body `{ "version": N }` trên PATCH/DELETE
- Server: `UPDATE ... WHERE id=? AND version=N` — 0 rows → **409 `SYNC_CONFLICT`**
- Client nhận 409 → **full refresh** từ GET (không merge partial server-side GĐ1)
- **Last-write-wins** chỉ sau client refresh — không silent overwrite

**QA bắt buộc (GL-16 / AC-PLAT-01..03):**

- User sửa Watchlist trên App và Web trong vòng 2 giây → một phía 409 → sau refresh hai kênh khớp

| `PAYWALL`          | 403                                    | User Free/Anonymous truy cập field Premium                                                      | No                    | Hiển thị Paywall + CTA nâng cấp             |
| `TIER_EXPIRED`     | 403                                    | Subscription hết hạn; JWT tier stale                                                            | No                    | Redirect trang gói (SCR-003 / WEB-003)      |
| `RATE_LIMITED`     | 429                                    | Vượt quota §23.2                                                                                | Yes sau `retry_after` | Backoff + retry                             |
| `FEED_DEGRADED`    | 200 + header `X-Data-Status: degraded` | Data Provider chậm/mất — §16.1                                                                  | No                    | Banner + serve cache; không hiển thị số giả |
| `SYNC_CONFLICT`    | 409                                    | `version`/`If-Match` không khớp khi PATCH Watchlist/Alert — user sửa đồng thời 2 kênh (§24.4.1) | No                    | Full refresh GET; không merge local         |
| `FEATURE_DISABLED` | 404                                    | Feature flag tắt — §24.7                                                                        | No                    | Thông báo tính năng tạm ẩn                  |
| `MAINTENANCE`      | 503                                    | Maintenance mode bật — §24.7                                                                    | Poll `/system/status` | Banner bảo trì                              |
| `PROVIDER_TIMEOUT` | 504                                    | Upstream Data Provider/API timeout                                                              | Exponential 3x        | Nút retry                                   |


**Response body chuẩn (4xx/5xx):**

```json
{
  "error": {
    "code": "SYNC_CONFLICT",
    "message": "Dữ liệu đã thay đổi trên thiết bị khác. Vui lòng tải lại.",
    "details": { "resource": "watchlist_items", "expected_version": 3, "current_version": 5 }
  }
}
```

**Idempotency:** Mutations dùng header `Idempotency-Key: uuid` — Redis TTL 24h — tránh duplicate Watchlist/Alert khi client retry (§4.2.1 backpressure).

**Retry policy (internal):**

- Kafka consumer: max 3 retries → DLQ topic `dead-letter`
- Data Provider reconnect: exponential 1s→30s, max 10 min circuit open
- Payment webhook: at-least-once + idempotent `external_id` UNIQUE
